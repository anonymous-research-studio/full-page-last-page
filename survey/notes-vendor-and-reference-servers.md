## Key Question 1: What does each server's list/search tool result contain, and how are "more results" and the END signalled? (evidence table)

### Takeaway
Across 19 vendor servers and 9 MCP reference servers (42 classified tool rows), no single convention dominates. The most common outcome is no in-result signal at all (12 rows, often with a silent default cap of 10 to 100 and sometimes a "Found N" count that equals the page size), followed by explicit end values (10 rows), end-by-omission (8 rows), total-only (6 rows) and natural-language notes (5 rows). The same server often mixes conventions: GitHub's server returns GraphQL `pageInfo` for `list_issues` but a bare JSON array with the Link header discarded for `list_pull_requests` and `list_commits`.

### Cited Findings

Category codes: A = explicit end value (false / null / empty string / `done: true`); B = end by omission (field present when more, absent at end); C = total only (no cursor or has_more); D = natural-language note in the result; E = no signal (silent cap); X = server claims exhaustive retrieval; ? = could not determine. "PT" = upstream JSON passed through largely unmodified.

### Inferences
- The six servers that pass upstream JSON through (Slack, Notion local, Salesforce, Square, PayPal, Microsoft Graph Enterprise) inherit whatever end encoding the upstream API uses. That yields a mix of empty string (Slack), null plus false (Notion), `done: true` (Salesforce), and field omission (Square, PayPal, Graph). Pass-through therefore does not imply an explicit end value.
- Reformatting servers drop upstream metadata more often than they add it. Concrete drops: Brave (all metadata), GDrive search (`nextPageToken` not requested), archived GitHub `list_issues` and current GitHub `list_pull_requests`/`list_commits` (REST Link header), GitLab (`X-Next-Page`/Link), Stripe historical (`has_more`), Cloudflare `zones_list` (`result_info`), Box (`total_count`, offset), Elastic (`total.relation`).
- The REST Link header never reaches the model in any surveyed server. Every Link-header API in the sample (GitHub REST, GitLab) either dropped it or replaced it with a total. The paper's "Link header serialized into the result" condition is therefore more generous than deployed practice, which goes straight to the no-signal case.
- "Full page means more" is itself deployed as a heuristic. Grafana computes `hasMore` as `len(page) == limit` and Cloudflare/Sentry/GDrive give the model a count equal to the rows returned. On an exactly full last page, Grafana emits an explicit but wrong `hasMore: true`, which is the paper's title case in reverse.
- Several servers give a "more exists" signal with no way to act on it: Slack history (`has_more`, no cursor param), Notion remote rows mode (`has_more`, "Rows mode does not return a cursor."), Salesforce (`nextRecordsUrl`, no queryMore tool), MongoDB `find` (total, no `skip`). The paper's metric (does the model keep fetching) does not apply cleanly to these; the relevant behaviour is whether the model reports incompleteness.

### Gaps
- Linear (hosted only; docs name no tools and give no outputs: "centrally hosted and managed" — [Linear MCP docs](https://linear.app/docs/mcp)), HubSpot (remote server at mcp.hubspot.com; docs give no tool names or outputs — [HubSpot MCP](https://developers.hubspot.com/mcp); GitHub `HubSpot/mcp-server` is empty), Asana (docs give no outputs — [Asana MCP](https://developers.asana.com/docs/mcp-server)), Shopify (Storefront MCP catalog tools "have been removed" in favour of UCP; no pagination text — [Shopify docs](https://shopify.dev/docs/apps/build/storefront-mcp/servers/storefront)), Zendesk and Airtable (no official repo found under their GitHub orgs; not searched further): could not determine.
- Stripe's current remote `stripe_api_read` output: could not determine (closed source, no example output in docs).
- Atlassian's text `content` block: issue #213 reports it is byte-identical across clients, but no issue quotes it, so whether it carries `pageInfo` is undetermined.
- Upstream end encodings marked "inferred" (PayPal `links`, Graph `@odata.nextLink`, Salesforce `done`/`nextRecordsUrl`, Brave `more_results_available`, Stripe default limit 10, Box default limit 30, ES default size 10, Go `iterator.Pager` empty token) were not fetched from vendor docs in this pass.

## Key Question 2: Raw upstream JSON, reformatted JSON, or text/markdown, and which channel does the model actually see?

### Takeaway
Of the 42 classified rows, 9 pass upstream JSON through (fully or as an envelope), 10 return text or markdown with an embedded count or note, and most of the rest return reformatted JSON (the remote Notion and Neon rows are documented without output format). A newer complication is the `structuredContent` channel: Atlassian's pagination fix lives only in `structuredContent`, which Atlassian reportedly withholds from unrecognised clients, so the same tool call can carry an explicit end value for one client and not for another.

### Cited Findings
- Text/markdown results: GDrive search, Brave, fetch, git_log, Sentry `search_issues` (markdown with "Found **N** issues"), Elastic `search` ("Total results: N, showing M."), MongoDB `find`/`aggregate`, Salesforce (prefix "SOQL query results:" + JSON), Azure MySQL query (text rows + placeholder row). Sources in the Q1 table.
- MCP spec 2026-07-28: "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block." — [tools.mdx#L500](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/dae694f61a31f7a3ec2af3aff709e11f70f61e48/docs/specification/2026-07-28/server/tools.mdx#L496-L500)
- Atlassian #213 (open): "`structuredContent` appears to be conditional on the MCP `clientInfo.name` sent in the `initialize` handshake." Reporter's table: `clientInfo.name` `mcp` and `riverpool-mcp` got `structuredContent` absent; `claude-code` and `cursor` got it present. "The `content` text block is **byte-identical** across all four names. Only the structured channel differs." — [atlassian-mcp-server#213](https://github.com/atlassian/atlassian-mcp-server/issues/213)
- The Atlassian fix was described by staff as applying to "structured content": "`searchJiraIssuesUsingJql` structured content now includes cursor pagination metadata via `pageInfo`." — [#118](https://github.com/atlassian/atlassian-mcp-server/issues/118)

### Inferences
- For servers that emit both channels, what reaches the model depends on the MCP client, not only on the server. A controlled experiment that injects the signal into the tool-result text the model reads matches clients that forward `content`; clients that forward `structuredContent` may see a different payload. This is worth one sentence in the paper's threats-to-validity or external-validity section.
- Text-formatted results (10 rows) put completeness information into prose ("Found 10 files", "Found **10** issues", "Total results: 87, showing 10.") rather than fields. That makes the paper's natural-language-note condition and its no-signal condition the two most ecologically relevant forms for text-returning servers.

### Gaps
- I did not test any client to see which channel it forwards to the model; client behaviour is out of scope for this survey and is covered by the "could not determine" note above.

## Key Question 3: How is the END marked in practice?

### Takeaway
End encodings split roughly evenly between explicit values (false, null, empty string, `done: true`) and omission, with a large residual of silence. Two explicit encodings conflict with the current MCP spec's own cursor rule: Slack and Google Cloud Storage use an empty-string token as the end marker, while MCP 2026-07-28 says an empty-string cursor "MUST NOT be treated as the end of results" for list operations.

### Cited Findings
- Explicit false/null: GitHub `list_issues` (`hasNextPage: false`), Atlassian post-fix (`hasNextPage: false, endCursor: null`), Notion local (`has_more: false`, `next_cursor: null`), Grafana `query_loki_logs` (`resultsTruncated: false`), Grafana `search_dashboards` (`hasMore: false`, heuristic). Sources in Q1.
- Explicit empty string: Slack (`next_cursor: ""`), Toolbox GCS (`nextPageToken` empty, inferred). Sources in Q1.
- `done: true`: Salesforce SOQL pass-through (field name inferred). Source in Q1.
- Omission: Notion remote list tools and backlinks, Square `cursor`, Azure MySQL `TablesTruncated`, Workspace `nextPageToken` (inferred), PayPal `links` (inferred), Graph `@odata.nextLink` (inferred). Sources in Q1.
- NL-note omission: fetch appends its truncation note only when content remains; Azure MySQL appends its placeholder row only when the cap is hit. Sources in Q1.
- Total equal to rows returned: Elastic ("Total results: N, showing N."), MongoDB ("resulted in N documents. Returning N documents."), GitHub search (`total_count` <= page). Sources in Q1.
- Spec rule, new in 2026-07-28: "Don't make any determination based on cursor value other than whether a non-null value was provided (e.g. an empty string is a valid cursor and thus **MUST NOT** be treated as the end of results)" — [pagination.mdx#L102-L107](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/dae694f61a31f7a3ec2af3aff709e11f70f61e48/docs/specification/2026-07-28/server/utilities/pagination.mdx#L102-L107). A grep of the same file in the 2025-06-18 and 2025-11-25 spec folders finds no "empty string is a valid cursor" sentence (0 matches each), so this wording was added in the 2026-07-28 version.

### Inferences
- An agent that has internalised the MCP list-pagination rule (empty string is a real cursor) and then sees Slack's `next_cursor: ""` could plausibly keep fetching. The paper's stimulus set has no empty-string end condition, which could be noted as a limitation or a follow-up arm. This is an inference; no source tests it.

### Gaps
- No source measures how models interpret empty-string end markers.

## Key Question 4: Silent caps and dropped upstream metadata

### Takeaway
Silent default caps are common and small: 10 (GDrive search, git_log, Sentry, MongoDB `find`, Slack history, Loki), 20 to 30 (Brave, GitHub REST lists, Box), 50 to 100 (BigQuery 50, Grafana search 50, Supabase logs 100, Gmail 100). In 12 rows the cap comes with no in-result signal. In two of those (GDrive, Sentry) the result also prints a count that equals the page size, and three more rows outside that bucket (Cloudflare `zones_list`, Grafana `search_dashboards`, Atlassian pre-fix) carry a count or total field equal to the rows returned. All five read like a total.

### Cited Findings
- Count-equals-page-size outputs: GDrive `Found ${n} files:` with `pageSize: 10`; Sentry `Found **${issues.length}** issue(s)` with default 10; Cloudflare `count: zones.length`; Grafana `Total: len(searchResp.Payload), // Grafana doesn't return total count`; Atlassian pre-fix `totalCount` equal to `maxResults`. Sources in Q1.
- Caps with no mention in the description: Supabase `get_logs` (`limit 100` in SQL; description silent), Toolbox BigQuery (50 rows), Sentry (description lists query syntax but not that only 10 are returned unless `limit` is raised). Sources in Q1.
- Caps disclosed only in the description (not in the result): Brave ("Maximum 20 results per request, with offset for pagination."), GitHub `list_commits` ("Returns at least 30 results per page by default ..."), Neon ("Returns every page. Pass limit to cap how many. There is no `cursor` argument."), Azure Cosmos vector search ("Use --count to control how many documents are returned (1-20, default is 10)" — [ItemVectorSearchCommand.cs#L23](https://github.com/microsoft/mcp/blob/cd2556e5c60426660b55b09ac6cdf44ed559bdd9/tools/Azure.Mcp.Tools.Cosmos/src/Commands/Item/ItemVectorSearchCommand.cs#L23)).
- Stripe historical `list_customers` dropped `has_more` from an API whose list objects carry it, and returned only IDs. Source in Q1.
- GitLab archived: because GitLab omits `X-Total` above 10,000 records (GitLab docs) and the server defaults to `"0"`, a search matching more than 10,000 projects would report `count: 0` alongside a full page of items (inferred from code plus docs; not executed).

### Inferences
- The typical deployed failure is a server that supplies a number that looks like completeness information but is not, rather than a server that hides a cursor. This is closest to the paper's `total_count` arm (33% continuation on a true last page, near the 38% no-signal rate), except that the deployed number is often the page size rather than the true total, which makes it worse.

### Gaps
- I did not measure how often the default caps bind in real use.

## Key Question 5: Does the tool description tell the model how to get more?

### Takeaway
Mostly no. Only a minority of descriptions explain the continuation protocol (GitHub `list_issues`, Brave, Notion remote list tools, Toolbox GCS via parameter text, Neon's "no cursor" statement). Most tools expose `page`/`perPage`/`limit` parameters with generic text such as "Page number for pagination (min 1)" and say nothing about how the result will indicate more.

### Cited Findings
- Explains protocol: GitHub `list_issues` ("use the 'endCursor' from the previous response's 'pageInfo' in the 'after' parameter"); GitHub also returns an error that teaches the protocol if `page` is passed: "This tool uses cursor-based pagination. Use the 'after' parameter with the 'endCursor' value from the previous response instead of 'page'." — [issues.go#L3893](https://github.com/github/github-mcp-server/blob/f38526264abb14961b32cea386e38ec6d3cf674f/pkg/github/issues.go#L3893). GitHub's generic cursor param text: "Cursor for pagination. Use the endCursor from the previous page's PageInfo for GraphQL APIs." — [params.go#L380-L383](https://github.com/github/github-mcp-server/blob/f38526264abb14961b32cea386e38ec6d3cf674f/pkg/github/params.go#L380-L383)
- Generic only: GitHub page/perPage ("Page number for pagination (min 1)", "Results per page for pagination (min 1, max 100)") — [params.go#L348-L357](https://github.com/github/github-mcp-server/blob/f38526264abb14961b32cea386e38ec6d3cf674f/pkg/github/params.go#L348-L357); PayPal ("retrieves a list of invoices with optional pagination parameters") — [prompts.ts#L53-L57](https://github.com/paypal/agent-toolkit/blob/a3aa963960caf32912691a759879a8ce7a6018b2/typescript/src/shared/prompts.ts#L53-L57).

- Because most descriptions are silent, the in-result signal is usually the model's only cue, which supports the paper's design choice of varying only the result encoding.

## Key Question 6: MCP specification status (Oct 2026): is pagination or completeness standardized for tool results?

### Takeaway
No. As of the 2026-07-28 specification (the latest dated version; spec repo HEAD dated 2026-10-23), pagination is defined only for `resources/list`, `resources/templates/list`, `prompts/list`, and `tools/list`. `CallToolResult` has no cursor, has-more, or completeness field. The new `resultType` field (`"complete"` | `"input_required"`) describes whether a request finished or needs more input; it does not describe dataset completeness. Proposals to standardize tool-result pagination exist but were closed without adoption, and the original 2025 issue remains open.

### Cited Findings
- Scope of pagination: "The following MCP operations support pagination: `resources/list` ... `resources/templates/list` ... `prompts/list` ... `tools/list`" — [pagination.mdx#L83-L90](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/dae694f61a31f7a3ec2af3aff709e11f70f61e48/docs/specification/2026-07-28/server/utilities/pagination.mdx#L83-L90); "Clients **SHOULD**: Treat a missing `nextCursor` as the end of results" — [pagination.mdx#L97-L100](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/dae694f61a31f7a3ec2af3aff709e11f70f61e48/docs/specification/2026-07-28/server/utilities/pagination.mdx#L97-L100)
- `PaginatedResult.nextCursor`: "An opaque token representing the pagination position after the last returned result. If present, there may be more results available." — [schema.ts#L1068-L1074](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/dae694f61a31f7a3ec2af3aff709e11f70f61e48/schema/2026-07-28/schema.ts#L1068-L1074). (So MCP's own list convention is end-by-omission, the encoding that left fetching near the no-signal rate for the Link-header arm in the interim results.)
- `CallToolResult` fields are `content`, `structuredContent`, `isError` (plus inherited `_meta`, `resultType`) — [schema.ts#L1809-L1839](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/dae694f61a31f7a3ec2af3aff709e11f70f61e48/schema/2026-07-28/schema.ts#L1809-L1839)

- Issue #798 / Discussion #799 (2025-06-19) proposed a `paginationHint: true` annotation and a result block `{"pagination": {"hasMore": true, "nextCursor": "opaque-token"}}`; the author added "This is more about giving the model a predictable way to request additional data and know when it's at the end." ### Inferences
- Because the protocol leaves tool-result completeness to each server, every vendor invents an encoding, which explains the spread in Q1. The paper can state that the protocol layer offers no standard completeness field for tool results as of the 2026-07-28 spec.
- The word "complete" in `resultType` could be misread by readers or models as dataset completeness. It means the request finished. Worth a footnote if the paper discusses MCP.

### Gaps
- I did not search SDK repositories (TypeScript, Python) for helper conventions, or non-GitHub channels (Discord) where the September 2026 Discussions closure redirected conversation.

Most consequential examples (with sources in Q1):
1. **Atlassian `searchJiraIssuesUsingJql` (remote, very widely deployed).** The same production tool went through three completeness regimes in 2026: `totalCount` equal to the page size with no cursor (reported 2026-03-20), then explicit `hasNextPage: false, endCursor: null` (staff fix 2026-06-04), then a false explicit end (`hasNextPage: false` with `remainingCount` > 0 and 5-node cap, onset 2026-08-14). Users documented the stakes directly: "we can't get accurate counts for 6 out of 10 metrics", "Six issues retrieved out of 45, no cursor left, no error", and "Claude Code stalls on the last page." This is the strongest real-world stakes evidence for the reviewer's objection.
2. **"Found N" equals the page size (GDrive archived reference server, Sentry `search_issues`).** The model sees "Found 10 files" or "Found **10** issues" with a default cap of 10 and no cursor. This is a deployed version of the paper's total-like condition in its most misleading form, shipped in Anthropic's original reference server and in Sentry's current official server.
3. **GitHub's official server mixes regimes in one product.** `list_issues` returns GraphQL `pageInfo` (explicit end, matches the paper's best-performing secondary form) while `list_pull_requests` and `list_commits` return bare arrays with the REST Link header discarded (no signal). The Link header never reaches the model in any surveyed server.
4. **Grafana `search_dashboards` encodes "full page means more".** `hasMore := len(searchResp.Payload) == int(limit)` and `Total: len(searchResp.Payload)` mean an exactly full last page carries an explicit but false `hasMore: true`. This is the paper's title condition hard-coded into an official server.
5. **The paper's secondary forms are deployed.** Elastic ("Total results: N, showing M.") and MongoDB ("resulted in N documents. Returning M documents.") ship the natural-language-note form, and Azure MCP's MySQL query ships the placeholder-row form ("... (output limited to 10,000 rows for security and performance reasons)"). Stripe's historical toolkit dropped `has_more` entirely.

### Inferences
- Mapping to the interim results (gpt-oss-120b): explicit end values (0-1% over-fetch on a true last page) appear in 10 of 42 rows (24%). Total-only (33% over-fetch) and end-by-omission (the Link-header analogue, 30%) together cover 14 rows (33%), and no-signal rows (34% continuation when more exist, 38% on a true last page) cover 12 rows (29%). So roughly three in five deployed rows use an encoding that, in the experiment, left behaviour close to the no-signal baseline. This mapping treats "field omitted at end" as equivalent to the omitted-Link-header arm; that equivalence is an inference because the stimulus omitted a serialized header, not a JSON key.
- The deployed data also suggests one arm the experiment lacks: an explicit end value that is wrong (Grafana heuristic, Atlassian August regression). If the paper claims explicit end values stop fetching, the deployed counterexamples show the risk of trusting them, which strengthens the motivation for model-side verification.

- Counts are per tool row chosen by me (1 to 4 most important per server), not usage-weighted. No public data on call volume per tool was found.
- Seven servers in the assignment list could not be classified (see Q1 Gaps).
